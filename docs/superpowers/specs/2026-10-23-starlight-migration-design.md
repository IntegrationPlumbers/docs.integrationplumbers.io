# Starlight migration: replace the Jekyll theme with Nathan's Astro Starlight site

Date: 2026-10-23
Author: Andre Beaumont, with Claude
Status: approach approved in conversation 2026-10-23; builder check done, resolutions below

## Intent

docs.integrationplumbers.io is a Jekyll site on the stock `pages-themes/slate`
remote theme, built by GitHub Pages' legacy builder from `main`. It looks dated
and has no sidebar, no page outline and no search. Nathan built a replacement
on Astro + Starlight (https://github.com/IntegrationPlumbers/ip-docs-starlight,
one commit, 2026-10-23, preview at
Nathan's preview deployment (internal URL, shared in the team channel)). His site is a
build step over this repo's existing Markdown: a converter reads
`<product>/*.md` and `_data/<product>_nav.yml` and produces Starlight content.
The page text is unchanged.

We want Nathan's site to become the real docs site. The decision made with the
user: fold Nathan's Astro project into this repo and deploy it to GitHub Pages
from a GitHub Actions workflow, rather than moving the content into his repo or
pointing DNS at his Dokploy host.

## Why fold in, not cut over

- Four plug-in repos generate the Markdown and nav YAML and push them here
  (`_data/mysql_nav.yml` carries the "GENERATED by tools/docs/build_site.py in
  the ip-oem-mysql-plugin repo" marker). The lint, Slack and Monday CI also
  lives here. Nathan's converter consumes this layout untouched, so nothing
  upstream changes.
- Hosting stays on GitHub Pages at the same domain. Nathan's `public/CNAME`
  already names it. GitHub Pages resolves `/page` to `page.html` natively, so
  his nginx config is not needed.
- A single reviewable PR replaces the theme. Nathan reviews it; his repo stays
  as the origin of the work and can be archived afterwards (his call).

## Goals

1. Every page on the live site renders through Nathan's Starlight theme with
   the same text, images, videos, tables and `<details>` blocks as today.
2. Every existing URL and anchor keeps working. The one accepted exception:
   each product landing page moves from `/<product>/` to `/<product>.html`,
   and `/<product>/` serves a redirect to it (Nathan's `postbuild-pages.mjs`
   already does this). Deep links such as `/mysql/getting-started.html#before`
   are unchanged.
3. The `<product>/ai/*.md` guides and `<product>/downloads/*` keep being served
   as raw files at their current paths (the AI troubleshooting guides are loaded
   by assistants as plain Markdown). Nathan's converter already copies them to
   `public/`.
4. A merge to `main` deploys automatically. A PR that breaks the build is
   caught before merge.
5. The upstream generators and `scripts/lint-*.sh` need no change.
6. Local preview is `npm` only. The Docker + Jekyll procedure goes away.

## Non-goals

- Changing any page's wording, structure or URL scheme beyond goal 2.
- Restyling or extending Nathan's design. Ship it as he built it; iterate later.
- Carrying over his Dokploy deployment (`Dockerfile`, `nginx.conf`,
  `.dockerignore`, `scripts/package-preview.py`). Those stay in his repo.
- Moving the Markdown into `src/content/docs/` "for good" as his README
  suggests. The converter stays as a build step because upstream repos own the
  Markdown.

## Anti-goals (what would make this a failure)

- An upstream plug-in repo's next docs push lands and the site no longer builds,
  or builds with a page missing.
- A link in a Zoho KB article, a release note or a customer email stops
  resolving.
- `main` deploys a broken site because nothing checked the build on the PR.

## Constraints

- Public repo. Nothing internal (lab hosts, task ids, Monday links) may enter
  committed files; the existing lint rules already enforce this for pages.
- GitHub Pages must be switched from "Deploy from a branch" to "GitHub Actions"
  in repository settings. The deploy workflow should attempt this itself
  (`actions/configure-pages` with `enablement: true`); if the token lacks
  permission, a repo admin flips the setting once. The user is told either way.
- Node: Nathan's README requires 22.23.4 or later and his Dockerfile uses
  `node:24`. Pin the workflow and an `.nvmrc`/`engines` field to Node 24.
- The converter's output (`src/content/docs/`, `public/<product>/`,
  `src/sidebar.json`, `src/products.json`) is generated on every build and is
  not committed.

## Decisions already made (keep these)

### Repository layout

- The Astro project lives in a `site/` subfolder: `site/package.json`,
  `site/astro.config.mjs`, `site/src/`, `site/scripts/convert.mjs`,
  `site/scripts/postbuild-pages.mjs`, `site/public/` (with `CNAME` and
  `favicon.png`). Content directories, `_data/`, `scripts/` and `.github/`
  stay at the repo root, so upstream pushes and lint are untouched.
- `convert.mjs` takes the repo root as its source; the npm `build` script
  passes `..` (not Nathan's `../src/docs.integrationplumbers.io`).
- Product card metadata that today sits in the converter's `PRODUCTS`
  constant (name, fullName, icon, status, summary, supports) moves to
  `_data/products.yml` at the repo root, keyed by product folder. The
  converter reads it. Builds and the release date keep coming from each
  product's `index.md` release line, as Nathan's converter already parses them.
  Reason: docs PRs can update "Supports MySQL 9.7" without touching code, and
  an upstream generator could own it later.

### Removal of the Jekyll site

Delete `_config.yml`, `_layouts/`, `Gemfile`, `Gemfile.lock`, the tracked
`_site/` directory (35 files), and `assets/` unless a product page references
it (`grep -r "assets/" <product>/*.md` found none at design time; the three
PNGs were used only by the slate layout). Keep the root `CNAME` file as well
as `site/public/CNAME`; it is harmless and protects against a settings reset.
`README.md` stops being the home page (Nathan's `ProductGrid` is) and becomes
a real README: what the repo is, the layout, how to build and preview, how
pages get here from the plug-in repos.

### CI and deploy

- New workflow `deploy-pages.yml`: on push to `main`, checkout, Node 24,
  `npm ci` and `npm run build` in `site/`, upload `site/dist` as the Pages
  artifact, deploy. Concurrency group so two merges in a row do not race.
- `static-checks.yml` gains a `site-build` job on pull requests that runs the
  same convert + build (no deploy) and uploads `site/dist` as a workflow
  artifact for manual preview. It also runs a post-build internal link check:
  every `href`/`src` in `site/dist` that points inside the site must resolve to
  a file in `site/dist` (Nathan's `package-preview.py` has the logic; port the
  check, not the relative-URL rewriting). Dangling links fail the job.
- The existing `docs-lint` and gitleaks jobs are unchanged.

### Theme and behaviour

- Theme mode stays Auto (follows the OS), with dark as the base, as Nathan
  shipped it.
- Starlight features stay as configured: Pagefind search, right-hand "On this
  page" outline (h2 to h3), prev/next pagination, "Edit page" to the GitHub
  blob of the source Markdown, "Copy page as Markdown" / "View Markdown" served
  from the `.md` copy beside each page, `llms.txt`, Legal notices page
  assembled from each product's notice.

## Verification before the PR is called done

1. `cd site && npm ci && npm run build` succeeds from a clean checkout with no
   "missing media" warnings from the converter. (Done once already on
   2026-10-23 against Nathan's repo and current `main`: 77 pages, ~8 s.)
2. The set of `.html`, `.md`, `ai/*.md` and `downloads/*` paths in `site/dist`
   is a superset of the paths GitHub Pages serves today (compare against the
   URL list in the tracked `_site/` or a fresh Jekyll build), apart from the
   landing-page move in goal 2, which must have its redirect file present.
3. The internal link check passes.
4. A spot check in a browser of one page per product plus the home page, in
   light and dark, desktop and 390 px wide, matches Nathan's preview host.
5. After merge: the Actions deploy succeeds, https://docs.integrationplumbers.io
   serves the new site, `/mysql/` redirects, `/mysql/getting-started.html#before`
   lands on the heading, `/mysql/ai/troubleshooting.md` returns raw Markdown,
   search finds a term, and the Zoho KB screenshot workflow (which captures
   live docs URLs) is told the look has changed.

## Builder-check resolutions (Claude's calls, 2026-10-23)

A reviewer read the document cold and asked six questions. None needed the
user, so these are settled here as the author's calls.

1. **Old image URLs keep resolving.** Nathan's converter copies
   `<product>/images` into the content tree, so Astro optimises them and
   hashes them into `dist/static/`; the old `/<product>/images/...` paths
   vanish. The converter must also copy the raw image tree to
   `public/<product>/images/` so every old image URL still serves. Cost: the
   build output roughly doubles (about 37 MB today), which is well inside the
   GitHub Pages limit. Verification step 2 covers images too.
2. **Baseline for "what the site serves today"** is the live site's
   `/sitemap.xml` (77 URLs on 2026-10-23) plus every file under
   `<product>/images`, `<product>/ai` and `<product>/downloads` in the repo.
   The tracked `_site/` is stale and must not be used. The live site also
   serves `/robots.txt` with a `Sitemap:` line pointing at `/sitemap.xml`;
   Starlight emits `sitemap-index.xml`. Add `site/public/robots.txt` that
   allows everything and points `Sitemap:` at `/sitemap-index.xml`, and have
   the post-build step also write `dist/sitemap.xml` as a copy of
   `sitemap-index.xml` so Search Console and old references keep working.
3. **Converter strictness.** Fail the build (non-zero exit) when: a product
   folder has no entry in `_data/products.yml`; a nav entry names a page that
   does not exist; a product `index.md` yields no builds from its release
   line. Pages that exist but are absent from the nav (today
   `mysql/beta-pre-release.md`, `mssql/beta-pre-release.md`,
   `mssql/early-access.md`) build and stay reachable by URL, as they are on
   the Jekyll site; they are not added to the sidebar.
4. **How upstream changes arrive.** The recent history shows docs updates
   land as pull requests, so the `site-build` PR job is the gate. `main` is
   unprotected today; with GitHub Actions deployment a failed build leaves
   the previous deployment live, so a bad merge degrades to "not updated",
   not "broken". Making `site-build` a required check is a repo setting and
   is recommended to the user as a follow-up, not part of this PR.
5. **What `products.yml` owns.** Each entry: `name` (required), `fullName`
   (optional), `icon`, `status`, `summary`, `supports` (list). The home page
   description, the `llms.txt` header and the Legal page headings derive the
   product list from this file; the "Enterprise Manager 13.5 and 24ai"
   phrase stays literal. Summary text is owned by whoever edits the docs,
   through a normal PR.
6. **The link check covers anchors.** For every internal `href` with a
   fragment, the target page must contain an element with that `id`.
   External links are not checked.
